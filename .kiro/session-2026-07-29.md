### DTR — Weekend (Saturday/Sunday) Biometric Punches Now Reflected
- **Problem:** COS Non Teaching employees (and actually all employee categories) who rendered weekend overtime had their Saturday/Sunday biometric punches silently discarded — no DTR row was ever generated for those dates, so weekend OT never showed up on the DTR.
- **Root cause:** `DTRService::generate()` determined `day_type` per date via `getDayType()`, and unconditionally `continue`'d (skipped entirely, before even reading that day's logs) whenever `day_type === 'rest_day'` — i.e. every Saturday/Sunday for employees on the default Mon–Fri schedule. This applied to every employee category, not just COS.
- **User's decision (scope, confirmed explicitly):**
  1. Apply to **all** employees, not just COS Non Teaching.
  2. Worked weekend punches count as **regular hours** — no special overtime flag/pay logic.
  3. **No approval gate** for now (any punch reflects, regardless of prior OT authorization) — revisit later if needed.
  4. Just reflect the raw time punches — no special visual marker beyond existing UI.
- **Fix (`app/Services/HR/DTRService.php`):**
  - `generate()`: rest day is now only skipped if `getLogsForShift()` finds **no** punches for that date (`$isWorkedRestDay` flag added). When punches exist, a normal record is still created.
  - Late/undertime/overtime forced to `0` for a worked rest day — there is no scheduled time to compare against (schedule's `getTimeIn()`/`getTimeOut()` would otherwise silently fall back to the Mon–Fri default times, producing bogus late/OT numbers).
  - Stored `day_type` is `'regular'` (not `'rest_day'`) for a worked rest day specifically so `PrintCsc.vue`/`PrintBatch.vue`'s `spanLabel()` renders actual punch times instead of the "SATURDAY"/"SUNDAY" placeholder span it uses for un-punched rest days. `getAttendanceStatus()` still receives the original `rest_day` dayType internally (only affects its holiday branch, which correctly doesn't match) so present/half_day/absent logic is unaffected.
  - `recompute()` (used for manual edits to existing records / schedule changes) — mirrored the same rule using `$schedule->isWorkDay($date)` (or `! isWeekend()` fallback) directly, since a worked-rest-day record's stored `day_type` is already `'regular'` and can't be used to detect "this was originally a rest day" after the fact.
  - No frontend changes needed — `Show.vue`/`My.vue` calendar cells and `PrintCsc.vue`/`PrintBatch.vue` remark logic already key off `day_type`/`attendance_status` generically.

## Key Patterns Learned This Session
- `EmployeeSchedule::getTimeIn()`/`getTimeOut()`/`getLunchStart()`/`getLunchEnd()` silently fall back to the schedule's Mon–Fri default `time_in`/`time_out` columns when `daily_schedules` has no entry for that day-of-week (including Sat/Sun) — this is fine for `computeHoursWorked()`'s lunch-deduction heuristic, but dangerous for late/undertime/overtime comparisons on a day that was never actually scheduled. Any future "worked on an unscheduled day" feature must explicitly zero out those three metrics rather than trusting the schedule fallback.
- `day_type` on `DtrRecord` drives frontend rendering decisions (`PrintCsc.vue`/`PrintBatch.vue`'s `spanLabel()`, `Show.vue`/`My.vue` calendar `isWorkDay`) — when a "rest day" needs to display real data instead of a placeholder, store `day_type = 'regular'` rather than adding a new enum value, to get the correct display behavior for free without any frontend changes. (A distinct enum value would have required Vue template changes too.)
- `recompute()` and `generate()` in `DTRService` are structurally similar but not shared — a rule change in one's day-type gating logic must be mirrored in the other explicitly, since `recompute()` operates on an already-persisted record and can't rely on the original (pre-fix) `day_type` to detect "this was a rest day," because the fix itself changes what gets stored.
