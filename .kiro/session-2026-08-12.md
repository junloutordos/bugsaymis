## Key Patterns Learned This Session
- **Fixing one authoritative source (e.g. a service's `$isAuh` check) does not guarantee every consumer that needs the same fact was updated to match — grep for every place that gates on the old, wrong signal (`hasRole('AUH')`, a hardcoded `roles: [...]` array, a separate hand-rolled switch) before declaring a role-derived-from-headship bug fully fixed.** This exact bug had to be fixed three separate times in one thread — `ApprovalInboxService` (visibility/count), then `navigation.js` + `ApprovalInboxController::isApprover()` (sidebar link + GET /inbox guard), then `authoriseApprove()`/`resolveLeaveStage()`/`delegateApprove()`'s action-mapping (the actual POST approve action) — because each one independently re-implemented "is this user allowed" instead of calling one shared helper.
- **A controller that hand-rolls its own authorization switch statement per request type (rather than delegating straight into the target controller's own `authorize()`/identity check) creates N places that can silently drift out of sync with the source of truth.** `ApprovalInboxController::authoriseApprove()` duplicates `LeaveApplicationController::approve()`'s stage logic instead of just calling it and letting it 403/422 on its own — every time the target controller's authorization logic gains a new case (like the AUH identity check here), the inbox's parallel switch must be manually updated too, or it silently blocks a request that the real endpoint would have allowed.
- **When an action string / stage-mapping `match`/`switch` has a catch-all `default` arm, audit whether every enumerated case that reaches that default is actually valid for it** — `delegateApprove()`'s `default => 'approved'` was correct for `campus_director` but silently wrong for the newly-added `academic_unit_head` stage (which only accepts `'recommended'|'rejected'`); the bug would have surfaced as a fresh 422 immediately after the 403 was fixed, one layer deeper in the same code path.
- **An inbox/discovery gate checking `hasRole('SomeRole')` for a role that was never actually created is a silent trap distinct from a permission bug** — the downstream approval action can be perfectly authorized (by identity, designation, or any other mechanism) while the *only* UI path to find the item is gated on a role nobody holds because it doesn't exist. Before trusting that a role-gated tab/feature is reachable, check `Role::where('name', ...)->first()` actually returns something, and prefer deriving visibility from the same authoritative source the real authorization check already uses (here, `academic_units.head_user_id`) over adding a separate RBAC role that must be manually kept in sync with headship/designation changes every school year.
- **A per-subject/per-entity schedule or permission check must be parameterized by the SPECIFIC entity being acted on, not a parent record's "default" value** — on any shared/co-owned record (PEHM class records, and likely other future co-teaching or multi-tenant patterns), a check that silently defaults to "the record's own X" instead of "this specific leaf/category/action's own X" will systematically fail for every owner except the one whose X happens to match the default. The PEHM co-teacher pivot (`class_record_teachers`, `subject_id`-scoped) already models this correctly for edit permissions (`GradingCategory::canEditOn()`) — the schedule-day check was the one place that pattern hadn't been applied yet.
- **A grid-level "is this day even open" pre-check and a final commit-time validation can have different strictness requirements** — the Assessment Calendar's day-cell grey-out (before a category is even chosen) must stay permissive (open if valid for ANY of the user's own pending categories), while the picker's final feasibility check (once a specific category/subject is chosen) must be strict and correct for that one subject. Collapsing both into one function using the same inputs caused the original bug's frontend half.
- **When a frontend's error handler assumes one specific backend error-response shape, every backend code path that doesn't match that shape fails silently, not loudly** — a vague bug report ("saving is not working," no error shown) is itself a strong signal to check for exactly this: a `message`-only response being parsed by code that only reads `errors`. Grep every 422/4xx response in the relevant controller for which ones include which keys before assuming the bug is in business logic rather than error-plumbing.
- **A boolean/classification flag derived from two independent code paths (a type-based shortcut AND a general formula) only needs ONE of those paths to be wrong for the bug to be user-visible, even if the general formula is provably correct** — `isMajor()`'s weight-share math was fine; the type-based `long_test_1/2` shortcut bypassing it entirely was the actual defect. When investigating "the formula gives a wrong answer," check for shortcut/early-return branches that skip the formula first.
- **A "derived and stored at save time" flag (`is_major`, and by extension anything computed from a category/config row at the moment an assessment is created) goes stale the instant that config is edited afterward — there is no automatic retroactive recompute.** Before writing off a mismatched flag as "must be a live code bug," check whether the row's `created_at` predates the referenced config's `updated_at`; if so, it's a snapshot-staleness data issue, not a currently-firing code defect, and needs a data backfill rather than (or in addition to) a code fix.
- **When "approved, run the check" surfaces unexpected data beyond the original hypothesis, report the new finding and re-scope before proceeding** — the read-only check was framed around confirming a QE/SE/PE bypass; it actually found zero cases of that but 4 cases of a different, previously-undocumented staleness bug. Surfacing that pivot explicitly (rather than silently substituting it for the original ask) let the user approve the now-larger scope (code fix + backfill) with full visibility.
- **Before pushing a hotfix, check `git log origin/main..main` — `main` can silently accumulate unrelated commits from parallel work/sessions between deploys.** Two deploys this session each bundled the hotfix with other, not-authored-this-session commits already sitting on `main` ahead of `origin/main`. Flagging the exact commit list before pushing (rather than assuming `main` only contains "my" change) gives the user an accurate blast-radius picture for a decision that's otherwise easy to get wrong by assuming a clean 1-commit deploy.

## Additional Key Patterns Learned (later same session)
- **A frontend `v-if` gated on a single terminal status must be re-checked every time a new terminal/post-terminal status is introduced elsewhere in the same workflow** — `Work Request`'s CSM rating flow added a second terminal state (`'Rated'`, coming after `'Completed'`) without anyone revisiting the print button's `status === 'Completed'` check written before that feature existed. Grep for every `status === 'X'` check across both Vue and Blade whenever a workflow gains a new terminal/post-X status.
- **Before diagnosing "the fix isn't deployed," verify with `git merge-base --is-ancestor <commit> origin/main` rather than grepping the live container for a string that might be the fix's own intentional fallback value** — searching prod for `'Flora Mae O. Tormento'` and finding it looked exactly like "the old hardcoded bug is still live," but it was actually the *new* code's deliberate fallback branch, comment and all. A live string match is not proof of which code path wrote it; check the actual git ancestry first.
- **When running production diagnostics through nested shell layers (bash → docker/ECS exec → tinker `--execute` string), namespaced class strings with backslashes (`App\Models\HR\LeaveApplication`) can silently lose their backslashes at an intermediate escaping layer, making an exact-match query return 0 rows that are actually present.** This produced two consecutive false "the data is empty" conclusions in one investigation. `LIKE '%ClassName'` (suffix match, no backslash needed) is a reliable way to sidestep this entirely when diagnosing through multiple shell hops; don't trust a sudden "count=0" from a query that logically should return rows without first re-verifying with an escaping-agnostic query.
- **A boolean success/failure return value from a helper (`performSign()` returning `false` on a bad PIN) is worthless as a safety mechanism if the caller never checks it and no user-facing error is surfaced** — the workflow (`processLeave()`) had already committed the stage transition by the time signing was attempted, so even checking the return value after the fact can only report the gap, not prevent it. The real fix had to move PIN verification *before* the state-changing call, not just add an `if (!$signed)` after it.
- **When a "the balance is being computed wrong" report turns out to have a plausible root cause matching a known anti-pattern (uninitialized `earned=0` on a flat-rate entitlement type), verify the *actual current data* before proposing a backfill number — a seemingly damning `earned=0` finding can be a column-semantics artifact (HR wrote the real balance to `carried_over` instead, exactly as designed for VL/SL) rather evidence of a live bug.** Computing and presenting "before/after" backfill numbers to the user, rather than assuming the fix should just be applied, is what surfaced that the naive backfill would have doubled every employee's balance — a mistake caught by the review step the safety guardrails call for, not by the initial code-reading investigation.
- **A `firstOrCreate()` on a model with a MySQL generated (`STORED`) column returns an in-memory object where that generated column is unset/zero immediately after an insert — the very next line reading `->balance` in the same request will get a stale value unless the model is re-fetched.** This is a distinct bug from "the seeded value is wrong" and only surfaces when the seeded `earned` value is actually nonzero (which is exactly when a new feature like `auto_grant_annual` would first exercise the code path) — a fix that only addresses the seed value without also handling the generated-column staleness will still silently fail in production the first time it's used.
