## Key Patterns Learned This Session
- **A "legacy mirror" table that's only written-to on specific write paths (assign/transfer) is a silent staleness trap** — `section_students` was correct by construction right after `EnrollmentController` wrote to it, but any assignment done through a different path (or before the mirror-write code existed) left rows silently stale with no error. When a table is described in code comments as a "mirror" or "legacy sync," grep for every write site and confirm 1:1 coverage with the authoritative table before trusting reads from it.
- **`orderByDesc('id')` is not a proxy for "most recent school year"** — row insertion order and school-year recency only coincide by accident. Any "latest X for this student" query spanning multiple school years needs an explicit school-year filter/join, not an id-based heuristic.
- **Before writing a new backfill/sync script, check if one already exists** — `artisan backfill:section_students` already existed, purpose-built for exactly this gap, and was idempotent (`updateOrInsert`) — just needed to be run in prod, no new command needed.
- **A production data problem and a code-durability problem are separable and can be fixed independently** — running the backfill fixed the user's immediate complaint before any deploy; the resolver refactor (deployed ~40 min later) is what prevents recurrence. Don't block the data fix on the code fix being ready, and don't skip the code fix just because the data fix already resolved symptoms.
- **When a legacy table can return partial rows (grade set, section null)**, a resolver's "no data" and "grade known, section pending" cases must be distinguished, not collapsed to the same null/empty result — the grade-7 pending-assignment case specifically needed `Grade 7` (no section suffix) rather than nothing.
