# Session Work Log — August 18, 2026

### Activity Management (AMS) — Certificates Could Not Be Generated for Newly Attended/Evaluated Participants (hotfix, deployed)
- **User report:** in the Activity Management module, cannot generate certificates for newly updated attendance participants and evaluated participants; check in production, fix it.
- **Investigation:** read `CertificateController::generate()`, `CertificateService::buildAndSave()`, `ActivityEvaluationEligibilityService`. Eligibility/generation logic looked structurally correct (fresh query per call). Found a secondary bug immediately (disk mismatch: writes to `disk('s3')`, but `CertificateController::streamPdf()` and `MyActivityController::downloadCertificate()` read from `disk('public')` — download-only bug, not the reported symptom). CloudWatch `/ecs/crcmis` turned out to be nginx access logs only (no PHP/Laravel app logs flow there — `LOG_CHANNEL=stderr` but Laravel's `\Log::warning()` calls apparently don't surface in the container's stdout/stderr the way expected, or logs were rotated/empty at time of check). Reproduced live in production instead: wrote a base64-encoded PHP diagnostic script, decoded+ran via `artisan tinker` inside an ECS-exec session (the same `$`/backslash shell-escaping issue seen in prior sessions — worked around with base64 transfer).
- **Root cause:** `CertificateService::buildAndSave()` called `Storage::disk('s3')->makeDirectory($dir)` before `put()`. S3 has no real directories; Flysystem's S3 adapter's `createDirectory()` tries to set an ACL on the placeholder object, which this bucket rejects (`AccessControlListNotSupported: The bucket does not allow ACLs` — Block Public Access / bucket-owner-enforced Object Ownership). This threw before `put()` ever ran, so **every** certificate generation attempt failed silently, caught by the controller's `try/catch` and just counted as "failed" in the flash message. Confirmed live: direct `put()` on the same key succeeded; `makeDirectory()` reproduced the exact ACL error.
- **Fix:** removed the `makeDirectory()` call (unique to this one file in the whole codebase — no other module does this). Also fixed the disk-mismatch download bug found during investigation (`CertificateController::streamPdf()`, `MyActivityController::downloadCertificate()` → `disk('s3')`).
- **Verification:** ran `CertificateEligibilityTest` (8 tests) — all passed, including one that already exercised the real `CertificateService` against `Storage::fake('s3')`. Verified live in production: regenerated a real certificate for participant 169/activity 9 — `certificate_path` went from `null` to a real S3 path, confirmed `exists on s3: yes`.
- **Deploy:** commit `d8e1ddbf` on `main`, pushed directly (working tree was already on `main`, not a feature branch — flagged to user, approved). GitHub Actions run `32099564265` completed successfully.

### AMS — Certificate Generation & Evaluation Link Sending Returned Gateway Timeout With No Success/Error Alert (hotfix, deployed)
- **User report (follow-up, live steering mid-session):** certificates now generate, but the request returns Gateway Timeout and never shows a success/error alert. Separately: sending evaluation links has the identical symptom.
- **Root cause:** both `CertificateController::generate()` and `ActivityController::sendEvaluationLinks()` looped over every eligible participant and did the heavy work (mPDF render + S3 upload + email, or just SMTP send) synchronously inside the HTTP request. For an activity with 226 present employees this exceeded the 120s `fastcgi_read_timeout`/`max_execution_time`, so the gateway dropped the connection before Laravel could respond — even though PHP kept running server-side and finished the work. Browser never saw the flash message.
- **Fix:** created `App\Jobs\AMS\GenerateActivityCertificates` and `App\Jobs\AMS\SendActivityEvaluationLinks` (both `ShouldQueue`), matching the existing `ProcessIssuanceRelease` convention (primitive IDs not models, single `tries`, timeout under the Redis `retry_after`, `failed()` handler, bell/push notification to the requester via `NotificationService` on completion or failure). Both controller methods now just dispatch the job and return immediately with an "started, you'll be notified" flash.
- **Verification:** rewrote `CertificateEligibilityTest` to assert `Queue::assertPushed(...)` instead of asserting synchronous side effects, moved the detailed generation-logic assertions to job-level tests calling `->handle()` directly. Added new `SendEvaluationLinksTest`. Also fixed a regression this surfaced: `EvaluationPeriodTest` was still faking `Storage::fake('public')` for certificate downloads — stale since the earlier `disk('s3')` download fix; updated to fake `'s3'`. Full `tests/Feature/AMS/` suite: 40/40 passed. Verified live: dispatched real jobs through the actual Redis queue in production (not just `.handle()` directly) and confirmed the worker consumed them with zero entries in `failed_jobs`.
- **Deploy:** commits `42f5cce3` (certificates) and `6124e76d` (evaluation links) on `main`. GitHub Actions runs `32101131421` and `32103844681`, both completed successfully.

### Infra — Queue Backlog Caused by Single Worker Process Serving Every Job (proactive fix, deployed, user-approved)
- **Finding (surfaced while verifying the two job-queue fixes above):** production Redis queue had a real ~150-job backlog. `supervisord-worker.conf` ran exactly one `queue:work redis` process (`numprocs=1`) draining one `default` queue, and **no job in the codebase used `->onQueue()`** — a single big batch job (`ProcessIssuanceRelease`, comment references "300+ emails") occupies the only worker for its full duration, head-of-line-blocking every small job dispatched behind it, including today's two new jobs. Confirmed by flooding the bulk lane with jobs and timing a concurrently-dispatched small job.
- **Fix:** tagged every job that loops over many recipients/records with `->onQueue('bulk')` in its constructor: `ProcessIssuanceRelease`, `NotifyAddedIssuanceRecipients`, `ResendIssuanceEmails`, `ProcessCoaIssue`, `NotifyAnnouncementJob`, `NotifyOedIssuanceUpload`, `ProcessBiometricImport`, plus today's `GenerateActivityCertificates`/`SendActivityEvaluationLinks`. Everything else stays on `default`. Split `supervisord-worker.conf`'s single `queue-worker` program into `queue-worker-default` (`--queue=default`, 120s timeout) and `queue-worker-bulk` (`--queue=bulk`, 700s timeout, same ceiling as before) — two independent supervisord-managed processes.
- **Infra change:** bumped the `crcmis-prod-worker` ECS task from 512 CPU/1024MB to 1024 CPU/2048MB (task definition revision 321, registered manually via AWS CLI + `update-service` before pushing code, so the deploy pipeline's `describe-task-definition`-based re-registration — which only swaps the image tag and otherwise preserves the live task def — would carry the bump forward automatically on the next deploy; confirmed it did, revision 322).
- **Verification:** full test suite run (1971 tests) — 43 failures, all confirmed pre-existing/unrelated via `git stash` comparison against the prior `main` commit (Auth, PPMP, FacultyLoading, ClassRecord, Profile, StudentIndex — none touch AMS/Issuance/Announcement/COA/Biometric). AMS + Issuance suite: 61/61 passed, including new `queue === 'bulk'` assertions. Live production test: flooded the bulk queue with 8 jobs, dispatched one default-lane job (`ExtractDocumentTextJob`) concurrently — **drained in 0.71s** while 7 bulk jobs were still pending, proving the split resolves head-of-line blocking.
- **Deploy:** commit `fefa8231` on `main`. GitHub Actions run `32111880543` completed successfully. Worker task confirmed running revision 322, image `fefa8231`, CPU 1024/memory 2048.

### Operational notes for future sessions
- **ECS exec quoting:** the AWS CLI's `execute-command --interactive --command` mangles `$`, backslashes, and nested quotes when passed inline PHP via `tinker --execute`. Reliable pattern: write the PHP script locally, base64-encode it (`base64 < script.php | tr -d '\n'`), embed the base64 string in a `bash -c "echo <b64> | base64 -d > /tmp/x.php && ... tinker --execute=\"require '/tmp/x.php';\""` command, redirect output to a file inside the container and `cat` it (session sometimes reports `Cannot perform start session: EOF` right after real output — harmless, output is already captured before that line).
- **CloudWatch `/ecs/crcmis` log streams are nginx access logs only** (`app/nginx/<task-id>`) — not a place to look for PHP exceptions or `\Log::` calls. Application-level debugging needs direct `tinker` reproduction via ECS exec instead.
- **ECS exec is not enabled on the `worker` service's task definition** (`enableExecuteCommand: false`) — only the `nginx`/web service has it. Can't shell into the worker container directly; verify worker behavior indirectly via Redis (`queues:default`, `queues:bulk` lengths) or DB (`failed_jobs`, `notifications`) from the web container instead.
- **Deploy pipeline preserves live task definition on redeploy:** `.github/workflows/deploy.yml`'s "Roll the worker service" step does `describe-task-definition` on the *currently running* task def and only swaps the image tag — any manual CPU/memory/other change made via `register-task-definition` + `update-service` ahead of a push will carry forward automatically on the next deploy, no workflow file edit needed.
