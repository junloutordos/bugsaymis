## 2026-09-10 (cont'd x6) - Committee Module Follow-ups: Delete Button, Load-Unit Inheritance, Dropdown Clipping, IPCR V2 Weight-Sum Bugs, Deletion Cascades, Members Tab (uncommitted as of this memory update)

- **Context:** direct continuation of the same-day Committee Module Overhaul entry above — this was a long back-and-forth troubleshooting session fixing several real bugs surfaced by actually using the new merged Catalog/Assignment UI, not new feature scope.
- **Delete button / load units audit:** confirmed the "More" (⋮) menu on the Index page's catalog table already had Export/Amend/Revoke/Delete (from the overhaul above) — nothing missing there. Confirmed the Core-vs-Support classification rule (`load_units > 0` → Core, else → Support, in `EmployeeFunctionSyncService`/`WorkDistributionPlanClassifier`) was already correctly implemented. Real gap found: **no UI anywhere** let anyone set a committee's `chairperson_load_units`/`member_load_units` (existing DB columns, read-only everywhere in the frontend) — added two inputs to the Index page's New/Edit Committee modal, threaded through `validateCatalogPayload()`/`storeCommittee()`/`updateCommittee()`, and exposed in `index()`'s catalog payload for edit-prefill.
- **Real bug found in that same fix:** `App\Models\Committee` (the "global" catalog model, `GlobalCommittee` alias) never had `chairperson_load_units`/`member_load_units` in its `$fillable` — Eloquent's mass-assignment silently dropped them on both `create()` and `update()`, so every save fell back to the DB column defaults (`1.00`/`0.50`) regardless of what the form sent, including a real `0`. Verified via `php artisan tinker` (`create([...'chairperson_load_units'=>0])` → DB actually stored `1.00`) before and after the `$fillable` fix. One production row ("Tech", id 25) was left at the wrong defaults from testing — flagged to user, not auto-corrected (didn't know their intended values).
- **"More" menu appearing to not open, then reported as clipped by the card:** two sequential bugs on the same dropdown menu. (1) The `v-click-outside` directive's `mounted()` hook attached its `document` click listener synchronously in the same tick the menu opened, so the just-completed open-click's own bubble-up immediately closed it — fixed with a `setTimeout(0)` deferral before attaching. (2) Once that was fixed, the menu was still visually cut off — root cause was `AppTable`'s default `card=true` wrapper (`overflow-hidden`, for the rounded-corner scroll clip) clipping the absolutely-positioned menu at the card boundary. First attempted fix (`card=false` + manual non-clipping wrapper div) was insufficient since `AppTable`'s *internal* `overflow-x-auto` scroll container still implicitly clips vertical overflow too. Final fix: replaced the in-cell `absolute` dropdown entirely with a single `<Teleport to="body">` menu positioned via `getBoundingClientRect()` of the clicked button (`fixed`, right-aligned, clamped to viewport) — the standard datatable row-menu pattern, immune to any ancestor's overflow/scroll state regardless of row position.
- **Sub-committee load-unit inheritance (approved change):** user wanted sub-committees to never ask for their own load units — always inherit the parent's. Removed the per-sub-committee load-unit inputs from the modal, replaced with an inheritance note showing the parent's live rates. Backend: `storeCommittee()`/`updateCommittee()` now set a sub-committee's `chairperson_load_units`/`member_load_units` from the **parent's own current values** at create/update time (a real stored value, not a live lookup, so `loadUnitsFor()`/roster-sync code needs no changes) — and `updateCommittee()` additionally cascades the parent's rate to **every** existing sub-committee via a bulk `subCommittees()->update()` after the per-item loop, so untouched subs still pick up a rate change on the parent.
- **IPCR V2 "weights sum to 200%, not 100%" error — two distinct root causes found across two rounds of investigation:**
  1. **Staleness bug:** `IpcrV2GenerationService::syncNewFunctions()` (the "Sync from Employee Functions" button) summed the **already-materialized** `ipcr_v2_core_items.weight_percent` (a frozen snapshot from generation/last-sync time) against a **freshly re-normalized** new `EmployeeFunction.weight_percent` — since `EmployeeFunctionSyncService::syncFromFacultyLoading()` re-normalizes every existing core weight whenever a new load-bearing committee assignment is added (shrinking others' shares to make room, still summing to 100% at the `EmployeeFunction` level), the *materialized IPCR item* never got that same refresh, so old-snapshot + new-fresh routinely overshot 100%. Fixed by refreshing each existing core item's `weight_percent` from its live `EmployeeFunction` (split evenly across multi-plan items, mirroring how they were originally materialized) immediately before the 100% sum check.
  2. **Deeper, separate bug (same error message, different trigger) — found via real production data (`user_id=1`, "Tech" account) after the staleness fix didn't resolve the user's actual repro:** a **manually-declared** Core Function (`EmployeeFunctionController`-created, `source_type` typically `manual`/`wdp`, always `sync_source_key = NULL`) reserves its own slice of a person's 100% Core budget, but `EmployeeFunctionSyncService::syncFromFacultyLoading()`'s load-based normalization (`$totalUnits`-derived weights for teaching/designation/committee Core rows) always assumed it owned the FULL 100% on its own, with zero awareness of any manual Core Function already claiming part of it. Fixed structurally (user chose "fix for everyone," not just a one-off data correction): compute `$manualCoreWeight` (sum of Core `EmployeeFunction` rows with `sync_source_key IS NULL`) and normalize the load-based pool against `100 - $manualCoreWeight` (clamped ≥0) instead of a flat 100, threaded through `syncTeachingGroup()`/`syncLoadGroup()`/`syncCommitteeAssignment()` via a new `$coreWeightBudget` parameter.
  3. **Opcache false alarm along the way:** after the first fix, user still saw the old error — root-caused to PHP-FPM's opcache serving stale pre-fix bytecode (CLI/tests have opcache disabled so my own verification never saw it) — `docker compose restart php` cleared it. Real lesson: don't assume a restart alone fixed a reported-still-broken bug without re-reproducing the *exact* scenario — the opcache theory was wrong for the SECOND round of "still broken," which turned out to be the actual different root cause (#2) above, found only by querying live prod `EmployeeFunction` rows directly rather than trusting synthetic reproductions.
- **Committee deletion never cascaded — reported as two symptoms, same underlying design gap:** (a) deleting a committee left its `FacultyCommitteeAssignment` rows dangling (`committee_id` had **no FK at all** — plain nullable `unsignedBigInteger`) and by extension its synced `EmployeeFunction`/materialized IPCR V2 items stuck forever; (b) deleting an Employee Function directly (`EmployeeFunctionController::destroy()`) left its already-materialized `ipcr_v2_core_items`/`support_items` row behind too — `employee_function_id` on those tables is `nullOnDelete()` **by design** (protects rated history) but nothing ever pruned the now-orphaned-and-unrated row itself, so "Sync from Employee Functions" kept showing deleted functions forever (they were never additive-only removed, only additive-only added).
  - Fix (a): `destroyCommittee()` now explicitly deletes the committee's (and sub-committees') `FacultyCommitteeAssignment`+`LoadAssignment` rows, re-syncs `FacultyLoad`, and re-runs `EmployeeFunctionSyncService::syncFromFacultyLoading()` per affected user — all BEFORE the committee row itself is deleted. Added a new migration giving `faculty_committee_assignments.committee_id` a real FK (`nullOnDelete`, deliberately not `cascadeOnDelete` — a committee's own deletion must not silently cascade-wipe FacultyLoad/IPCR history without going through the proper reconciliation path) as a DB-level safety net for any other/future deletion path; nulled pre-existing dangling `committee_id` values first so the constraint could be added at all.
  - Fix (b): centralized on `EmployeeFunction`'s own model — added a `deleting`/`deleted` model-event pair (`booted()`) that prunes any orphaned, **unrated** IPCR V2 item for every deletion path uniformly, instead of duplicating the logic in each controller/service that might delete a function. Also fixed `EmployeeFunctionSyncService`'s own stale-row cleanup, which used a bulk query-builder `->delete()` — Eloquent model events never fire for a bulk delete, so this path silently bypassed the new centralized pruning; changed to `->get()->each(fn ($f) => $f->delete())` so events fire per-row. Kept `IpcrV2GenerationService::pruneOrphanedItems()` (added during the same investigation, called at the top of every `syncNewFunctions()` run) as a secondary safety net matching rows already orphaned *before* this fix shipped (`employee_function_id IS NULL`).
  - **Real bug caught by the tests themselves, mid-fix:** the FK's `nullOnDelete()` action nulls `employee_function_id` on affected rows as part of the SAME delete statement — by the time a naive `deleted` event handler queried `where('employee_function_id', $function->id)`, that value was already gone (DB already nulled it), so the query found nothing and pruning silently no-op'd. Fixed by capturing the affected item ids in a `deleting` event (still BEFORE the delete/cascade happens) into a small static in-memory map keyed by function id (explicitly NOT a dynamic model property — Eloquent's magic `__set` would route that into `$attributes`, not a real instance property), then pruning by those captured ids in `deleted`.
  - All deletion-cascade behavior strictly preserves the pre-existing "never silently drop rated/logged work" rule (already established by `EmployeeFunctionSyncService`'s own cleanup) — anything with real `actual_accomplishment` data, or on a finalized/period-closed record, is always left untouched as history, verified by dedicated tests in both directions.
- **New "Members" tab on the Committee Show page (separate, approved feature within this session):** the Show page previously had no clean roster view — "Accomplishments & Ratings" was IPCR-item-centric and never surfaced the `committee_user.task` pivot field (already existed, just never displayed), and adding a member required leaving the page entirely to use the Index page's catalog modal. Added a default-active "Members" tab (name/role/task/effective load units incl. override indicator/term status, remove action) plus `addMember()`/`removeMember()` controller endpoints (append-one/remove-one on the `committee_user` pivot, distinct from the catalog modal's full-roster-replacing `syncCatalogMembers()`, so the Show page can never accidentally wipe the rest of the roster) gated by a new `canManageCommitteeRoster()` helper (admin OR that committee's own active chairperson/co-chair, reusing the same hierarchical rule `rateAssignment()` already established) — reachable by a chairperson without needing full `faculty_loading.manage`.
- **Tests added this session (all passing, cumulative across the fixes):** `CommitteeRosterMembersTest` (7), `CommitteeDeletionCascadeTest` (6), extensions to `EmployeeFunctionSyncServiceTest` (+3 for the weight-budget-reservation fix), `IpcrV2GenerationServiceTest` (+5 across both weight-sum-fix rounds plus the orphan-pruning safety net), `EmployeeFunctionControllerTest` (+2 for destroy-time pruning). Full regression sweep across Committee/EmployeeFunctions/IPCR V2 suites: 193 passed, 595 assertions, zero regressions at final check.

- **Pattern reinforced (recurs across many earlier entries too):** (1) a table column with no FK constraint is a standing invitation for silent orphaning the moment any code path deletes the "parent" row — always check `\d`/migration source for a real FK before trusting that deleting a row cleans up its dependents; (2) a DB-level cascade action (`nullOnDelete`) and an application-level "please also clean this up" expectation are two different mechanisms that must be reasoned about together, not assumed to compose automatically — a model event querying by the soon-to-be-nulled foreign key must capture its data in a `deleting` (pre-cascade) hook, not a `deleted` (post-cascade) one; (3) when a user reports "still broken" after a fix that tests confirm works in isolation, don't default to blaming caching/opcache — re-verify against the user's actual live data first (this session's second weight-sum bug was a completely different root cause hiding behind an identical error message).
